## Prior art used

### OpenAI Codex / Agents
- Codex Cloud: each task runs in an isolated workspace; continuation belongs to the original task, while a new task gets a separate workspace.
- Codex/App Server: persistent thread identity; explicit `thread/start`, `turn/start`, completion status, and resumable thread state.
- Agents API: harness owns long-running session state while the application supplies tools and receives events.
- Codex/agent security: sandbox isolation, restricted network, server-side/vaulted credentials, explicit allowed tools, and fail-closed required tool initialization.
- Codex multi-agent: parallel subagents are best for independent work; shared write-heavy state requires coordination.
- Structured outputs/repair-loop guidance: use schemas and keep deterministic validation separate from model review/repair.

### A2A
- Separate `contextId` from server-generated `taskId`.
- Nonterminal interrupted states for `input-required` and `auth-required`.
- Terminal tasks are not restarted; follow-up work is linked explicitly through task/context references.
- Results are artifacts/history attached to the task, not a replacement for task identity.

### LangGraph
- Durable checkpointer + `thread_id`.
- `interrupt()` pauses for human/user input and later resumes the same durable state.
- Distinct recovery classes: transient, model-recoverable, user-fixable, compensating, unexpected.
- Persist raw state, not presentation-only text.

### Temporal
- At-least-once execution requires idempotent handlers.
- Unique workflow IDs / duplicate rejection are a proven route toward exactly-once effects.
- Cancellation is a propagated request; it is not evidence that external side effects were undone.

### OPA
- Keep policy decision separate from enforcement.
- Persist decision identifiers, trace/span identifiers, policy/bundle revision, input/result and timestamp for later audit.

### Icarus-native prior art already in Teamchat
- Effect Contract and independent readback.
- Expected revision + idempotency key + immutable checkpoints/events.
- AAR L2-style detached verifier and signed evidence receipt.
- Same-task phone readback and owner receipt requirement.
- Broker-side secret custody and tool/provider allowlists.

# 1. Canonical identity model

Icarus must stop treating model session identity as task identity.

```text
context_id
  └── task_id                    canonical unit of work
       ├── revision              monotonic task-state revision
       ├── execution_run_id      one executor attempt/run
       ├── provider_session_id   replaceable model/harness thread/session
       ├── policy_decision_id    authorization/admission decision
       └── verification_id       independent adjudication/receipt
```

Rules:

1. `task_id` is generated by the Icarus control plane, never by the Android client or model.
2. `context_id` groups related tasks without conflating them.
3. Provider/Codex/Gemini/DeepSeek thread IDs are execution metadata only. A provider change MUST NOT change canonical `task_id`.
4. Every mutation carries `expected_revision`.
5. Every potentially effectful attempt carries an `idempotency_key` and `mutation_fingerprint`.
6. Verification/owner verdict is attached to the same `task_id` and observed revision it judges.

# 2. Canonical task lifecycle

The current Android enum is too coarse. In particular, a single terminal-looking `BLOCKED` state cannot safely represent auth waits, missing input, policy approval, unknown external outcome and permanent failure.

## Nonterminal states

- `SUBMITTED`
- `PREFLIGHTING`
- `READY`
- `WORKING`
- `INPUT_REQUIRED`
- `AUTH_REQUIRED`
- `APPROVAL_REQUIRED`
- `OUTCOME_UNKNOWN`
- `RECONCILING`
- `WORK_COMPLETE_AWAITING_VERIFICATION`
- `VERIFYING`

## Terminal states

- `PASS` — only after independent verification/authorized owner verdict.
- `FAIL` — evidence contradicts the requested effect or execution is irrecoverably failed.
- `REJECTED` — policy/authorization refuses the requested task.
- `CANCELLED` — cancellation is confirmed and any uncertain external effect has been reconciled.
- `SUPERSEDED` — replaced by an explicitly linked new task/revision.

## Legacy `BLOCKED` compatibility

Do not create new canonical terminal `BLOCKED` tasks. Translate the reason:

- needs user data → `INPUT_REQUIRED`
- needs service auth → `AUTH_REQUIRED`
- needs owner approval → `APPROVAL_REQUIRED`
- write may have occurred but cannot yet be proven → `OUTCOME_UNKNOWN` / `RECONCILING`
- policy refuses action → `REJECTED`
- unrecoverable execution failure → `FAIL`

This resolves the existing contradiction where a “terminal BLOCKED” task later needed a same-task recovery.

# 3. Required-action contract

Interrupted tasks carry a typed `required_action`; a status string alone is insufficient.

```json
{
  "type": "AUTH_REQUIRED | INPUT_REQUIRED | APPROVAL_REQUIRED",
  "reason_code": "stable_machine_code",
  "message": "safe human-readable description",
  "allowed_responses": ["..."],
  "resume_token": "opaque-server-value-or-null",
  "expires_at": "ISO-8601-or-null"
}
```

Security rules:

- `AUTH_REQUIRED` is not itself authorization.
- Auth scope/identity must be checked again when the task resumes.
- Android never supplies an authoritative Composio user/account identity.
- Auth redirects/tokens are opaque client data; raw provider credentials never enter app storage/logs.

# 4. Async gateway contract

The shell's current `submit(): TaskResult` contract is replaced conceptually by an asynchronous task handle.

## Logical operations

These are protocol roles, **not claims that these exact HTTP paths are currently deployed**.

- `createTask(problem, context?, idempotencyKey) -> TaskHandle`
- `readTask(taskId) -> TaskSnapshot`
- `readEvents(taskId, afterSequence) -> EventBatch`
- `provideInput(taskId, expectedRevision, input, idempotencyKey) -> TaskSnapshot`
- `resumeTask(taskId, expectedRevision, resumeToken?) -> TaskSnapshot`
- `requestCancel(taskId, expectedRevision, idempotencyKey) -> TaskSnapshot`
- `readCapabilities() -> CapabilitySnapshot`
- `submitOwnerVerdict(taskId, expectedRevision, verdict, evidenceRef, idempotencyKey) -> VerificationReceipt`

## TaskHandle

```json
{
  "context_id": "...",
  "task_id": "...",
  "revision": 1,
  "state": "SUBMITTED",
  "created_at": "...",
  "poll_after_ms": 1000
}
```

Creation returns quickly. Completion is observed through status/events, not by holding a single Android request open for the full task.

# 6. Actual capability snapshot

Tool choice must use live callability, not brand names or remembered connection state.

```json
{
  "snapshot_id": "...",
  "generated_at": "...",
  "tools": [
    {
      "tool_id": "...",
      "service": "GMAIL",
      "connected": true,
      "callable": true,
      "policy_allowed": true,
      "auth_required": false,
      "write": false,
      "reason": null
    }
  ]
}
```

Admission rule:

```text
requested service
  -> discover actual tools
  -> filter connected
  -> filter callable
  -> filter policy_allowed
  -> compare requested service to selected service/tool
  -> only then execute
```

If a user asks for Ubersuggest and routing selects Semrush, Icarus should fail admission with a deterministic `ROUTING_MISMATCH` before the external call. A service being connected does not prove a particular tool is callable or policy-authorized.

# 7. Effect contract for writes

Before an effectful call:

- `task_id`
- intended external effect
- target resource/account
- selected capability/tool
- mutation fingerprint
- idempotency key
- expected postcondition
- verification read path
- allowed verification window
- reconciliation/rollback rule

No tool success can transition directly to `PASS`.

Unknown write outcome:

```text
WORKING -> OUTCOME_UNKNOWN -> RECONCILING -> VERIFYING | FAIL
```

Blind retry is forbidden while outcome is unknown.

# 10. Permit / route binding

Before an executor can perform a side effect, bind an execution permit to:

- task ID + revision
- executor/agent ID
- route hash
- policy/ruleset version
- capability snapshot ID
- allowed tool IDs/scopes
- budget
- evidence contract
- expiry
- nonce

Any material executor/tool/route/cost/auth-scope change revokes the permit and returns the task to `PREFLIGHTING`.

# 11. Cancellation semantics

The current shell's local `cancel()` behavior must not imply that real-world execution stopped.

Correct contract:

1. Android requests cancellation for `task_id` + `expected_revision`.
2. Control plane records `CANCEL_REQUESTED` as an event while the canonical state remains nonterminal.
3. Executor/workflow cancellation propagates where supported.
4. If an external effect may already have happened, enter `OUTCOME_UNKNOWN` / `RECONCILING`.
5. Only after reconciliation may canonical state become `CANCELLED`.
6. Android never resets to IDLE until it has read the confirmed terminal state.

# 12. Structured output + raw preservation

For every model/reviewer/classifier:

1. persist raw output first;
2. validate against a versioned schema;
3. normalize deterministically;
4. preserve validation errors as evidence;
5. do not discard the raw result because one required field is absent;
6. transport/process success does not equal semantic success.

This directly closes the failure mode seen in the repo-ghost gateway pipeline.

# 13. Isolation and parallelism

Adopt the useful Codex/worktree pattern without making the worktree the source of truth:

- one isolated workspace/worktree per write-heavy execution run;
- read/research subagents may run in parallel;
- parallel writers do not share mutable working state;
- canonical task/checkpoint state remains above the worktree/model;
- merge/release is a controlled effect subject to the same verification rules.

# 14. Secret and network boundary

Follow the already-approved broker pattern plus current hosted-agent prior art:

- long-lived third-party secrets remain outside agent/client code;
- agent/runtime gets only scoped capability, never general credentials;
- outbound destinations are allowlisted where feasible;
- tool IDs/endpoints are allowlisted server-side;
- Android cannot supply arbitrary upstream hostnames or Authorization headers;
- required capability initialization fails closed.

# 15. Phone UI contract

The UI must expose the canonical state without exposing internal clutter.

Always bind the screen to:

- current `task_id` (short display form is fine)
- current revision
- objective
- state
- readable result
- evidence/receipt references
- required owner/user action when present

Owner verdict controls appear only for `WORK_COMPLETE_AWAITING_VERIFICATION` / `VERIFYING`, operate on the same task/revision, and reread the persisted receipt before the UI shows PASS.

# 17. Acceptance gates for the filled contract

The contract itself is ready for implementation only when:

1. logical state/identity schema passes deterministic validation;
2. terminal/nonterminal states are unambiguous;
3. revision + idempotency are required for mutations;
4. capability snapshot blocks a deliberate wrong-service selection;
5. executor cannot author a PASS receipt for itself;
6. cancellation cannot reset UI before server confirmation;
7. raw model output survives validation failure;
8. a provider-session swap preserves canonical task ID;
9. one same-task auth/input interruption resumes correctly;
10. a real live runtime trace fills the currently MISSING binding fields.
